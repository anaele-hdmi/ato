## 1. 制約：サーバ無し（GitHub Pages）で何ができるか

| 手段 | 可否 | 備考（確度） |
|---|---|---|
| **ビルド時データ取得**（Actions の `schedule` cron → fetch → build → deploy。コミット不要） | ○ | TLE・Kp予報・台風位置・雲画像を**日次〜数時間おき**に焼き込める。公開リポの Actions は無料枠制限なし（高）。cron の発火遅延は数分〜数十分（中） |
| 実行時に外部 API を直接 fetch | △ | CORS 許可のある API のみ。wheretheiss.at（中）、NOAA SWPC の JSON（中）、NASA GIBS タイル（中〜高）。可用性は保証されないので**ビルド時の値をフォールバック**に |
| ローカル保存（localStorage / IndexedDB） | ○ | 端末内のみ。Safari は非PWAで7日間無操作だとスクリプト書込ストレージを消しうる（中）。日誌は書き出し（Web Share / ダウンロード）で補完 |
| **Web Push 通知** | ✗ | 送信側サーバ（VAPID）と購読情報の保管先が必要。GitHub Actions から送るにも購読の受け口が無い |
| ローカル予約通知（Notification Triggers） | ✗ | Chrome の試験実装は終了（中〜高）。予約型の通知は Web では現状不可能 |
| ページを開いている間の `Notification` | △ | 開いていれば画面内表示で足りる。iOS は PWA インストール時のみ |
| Badging API | △ | Service Worker が生きている間だけ。予告用途には弱い |
| **`.ics` カレンダー書き出し** | ○ | 端末のカレンダーが代わりに通知してくれる。iOS/Android ともファイル共有経由で登録可（中〜高）。**「通知」の現実解** |
| 同時接続数・他者の存在 | ✗ | サーバ必須。Firebase / Supabase / Cloudflare Workers の無料枠で可能だが「サーバ無し」の条件外。WebRTC P2P もシグナリングが要る |
| 現在の視点を URL に符号化して共有 | ○ | `?t=…&cam=…&yaw=…`。受け手は同じ瞬間を見る。既に `?t=` はある |
| バックグラウンド再生（作業用BGM） | △ | デスクトップは可。iOS は Web Audio がバックグラウンドで止まる（中〜高）。`<audio>` 要素＋MediaSession に迂回しても iOS で確実に鳴る保証なし（低） |
| Picture-in-Picture（小窓で常駐） | △ | `canvas.captureStream()` → `<video>` → `requestPictureInPicture()`。Chrome/Edge デスクトップ・Android は可（中〜高）、iOS Safari は要実機（低） |

## 3. 各候補の補足（設計上の判断が要る点だけ）

### 3.1 「いま」とスキップ・スクラブ（#1 の副作用）

現状も `Date.now()` 起点だが、初回は「日の出2分前」へ進め、その後スキップ・地球儀スクラブで自由に離れる。実ISS同期を売りにするなら、次を決める必要がある。

| 論点 | 案 |
|---|---|
| 既定はいま／日の出前 | **いまを既定**、タイトル（暦ページ）に「日の出まで 12:30 ・ 少し前へ飛ぶ」を1行置き、選ばせる。「いまはただの夜の太平洋」を見せるリスクと「本物」の価値のトレードオフで、これは検証対象（§5） |
| 離れた後 | UI に「いまへ」（1ボタン）。離れている間は読み出しの時刻表示を薄く変える程度で、警告はしない |
| 通過予告との整合 | 予告は常に**実時刻**基準。ゲーム内で先回りして見ることもできる（それは予告ではなく下見） |

### 3.2 通過予告の中身（#2）

| 種別 | 計算 | 提示 |
|---|---|---|
| 上空通過（地心角 < 約5°＝直下から 500 km 圏） | 既存 `computeFrame` を 30 秒刻みで 48 時間走査。TLE 版なら SGP4 | 「次は今日 21:14（南西の空を通る）」 |
| 可視パス（観測者で太陽高度 < −6°、船は日照、仰角 > 10°） | 同上に条件追加 | 「肉眼で見える通過：木曜 19:52、4分間」＋ `.ics` 書き出し |
| 地点指定 | 地球儀ドラッグ（既存）／`geolocation` は**許可ダイアログが静けさを破る**ので既定は手動 | 複数地点可（故郷・旅先） |

### 3.3 暦ページ（#3）に載せる項目と情報源

| 項目 | 情報源 | 更新 |
|---|---|---|
| 日の出/日の入りまで、白夜期間（β角） | 既存計算 | 実行時 |
| 流星群（ふたご 12/13–14、しぶんぎ 1/3–4、ペルセウス 8/12–13、こと 4/22、みずがめη 5/5–6、オリオン 10/21、しし 11/17） | 静的表（日付の確度: 高） | 年1回 |
| 日食の本影（2027-08-02 皆既、2028-01-26 金環、2028-07-22 皆既）／月食 | 静的表（確度: 中。要照合） | 年1回 |
| オーロラ強度（実Kp） | NOAA SWPC をビルド時取得、無ければ乱数 | 3時間〜1日 |
| 台風 | NHC JSON（大西洋・東太平洋）。西太平洋は要調査 | 6時間〜1日 |

表示は**未来だけ**。「見た／見ていない」を暦に混ぜない（それは日誌の側）。

## 5. 検証の方法（サーバ無し）

### 5.1 何を測れるか

| 指標 | 方法 | 注意 |
|---|---|---|
| セッション長・視点別滞在・スキップ回数・「いまへ」使用 | クライアントで集計、localStorage に保持 | 就寝/常駐モードの時間は**別カウント**（注視していない） |
| D1/D7 再訪 | **クライアントが自分で判定**（初回日時を localStorage に保存、再訪時に経過日数を計算）し、外部カウンタに `return/d7/variant=A` のようなイベントを1発送る | GoatCounter・Plausible 等は cookie を持たず**サービス側では再訪を追えない**。クライアント判定なら可能。Safari 非PWA の7日消去でD7 が過小評価される（中）→ iOS では PWA インストールを促すか、D3 も併記 |
| 無作為化 A/B | 初回訪問時にクライアントが乱数で群を割り当て localStorage に固定。イベントに群を付ける | 真の無作為化。ただし検出力が問題（下記） |
| 何が理由で戻ったか | 再訪時に**一度だけ**、暦ページに1問（通過の予告／なんとなく／誰かのURL／その他） | 自己申告。n が小さくても機構の当たりは付く |
| 計測なし | 明示的に選ぶ | §14 の未決定を決める。計測を入れるならプライバシー表記1行 |

### 5.2 検出力の現実

- D7 が 10%→15% に上がる効果を α=0.05・検出力 0.8 で検出するには**各群約 690 人**（二比率検定の概算: 高）。個人開発の公開トラフィックでは月単位でも届かない可能性が高い。
- したがって公開版の A/B は「大きな効果の有無」しか言えない。**主要指標はセッション長（連続量・被験者内）**に置く。

### 5.3 少人数（6〜10人）での比較

| 項目 | 内容 |
|---|---|
| 設計 | 被験者内クロスオーバー。条件 A（暦＋予告あり）／B（なし）を `?v=` で固定し、各 1〜2 週間、順序は半々に入れ替える |
| 主要指標 | 週あたりの起動回数、セッション長の中央値（端末内ログを参加者が書き出して送る） |
| 副次 | 日誌の書き出し内容（何を見ていたか）、週末の10分インタビュー（「開いた時、何を期待していたか」） |
| 判断規則 | A で起動回数が全員一致で増えなければ「予告は効かない」と判定し、#4 実気象か #14 別軌道へ。セッション長が両条件で 5 分未満なら**再訪施策の前に #0** |
| 交絡 | 順序効果（慣れ・飽き）はクロスオーバーで相殺。可視パスの有無が週ごとに違う（数週の空白がある）ので、期間は**可視パスがある週を両条件に含める**よう予告表から逆算して組む |

| 1 | **再訪を目標にすべきか** | 無料の静的サイトで DAU を追う理由は薄い。本作の価値は「窓」であり、窓は毎日開けるものではなく、**開けたくなった時にそこにある**ことが価値。指標は「D7」より「初回セッションが満足で終わったか」「1か月後にまだ端末に残っているか」の方が製品の性格に合う。クライアントが再訪を求める理由（配信・評価・自己満足のどれか）を先に確認したい |
| 2 | **撮影を消したことで「行為」が無くなった** | 設計 §7.2 の「3〜5分で見終わる」リスクへの唯一の回答が撮影だった。#5 の自動日誌は行為を伴わないので保有効果は弱い。代替の最小の行為として **#11「この瞬間の URL」を1タップで残す**（しおり）を勧める。画像は作らないので現像・36枚の重さは無い |
| 3 | **実時刻同期は「最初の3分」を悪化させうる** | 「いま」既定だと、開いた時に夜の海しか無い確率が高い（夜側は約 35〜40%、海は約 70%）。§3.1 の「日の出まで／少し前へ」の1行で緩和するが、これは仮説。初回だけは現状どおり日の出前に置き、2回目以降を「いま」にする折衷も候補 |
| 4 | **開発順序** | review-2 §5 の 1〜6（陰影・霞・性能・iOS 初回無音・コンテキスト喪失）は未着手のはず。再訪施策より先に、戻ってきた人が iPhone で無音・黒画面にならないことの方が効く |
| 5 | **「気象に基づく雲」は気候学であって今日の天気ではない** | 公開文言で「実際の気象」と受け取られると #4 を入れる前に期待とずれる。README の表現は「気象学に基づく生成」と明記した方がよい |
| 6 | **暦ページは P4 と衝突する** | 「UI は消える」の原則に対し、暦は情報を「見せる」機能。タイトル画面に閉じ込め、船内には持ち込まないという線引きを design.md に書く |
| 7 | **計測の倫理と表記** | 外部カウンタを入れるなら、cookie 無しでも「訪問を数えています」の1行は要る。静けさと相反するので、入れないという選択も正当。ただし入れないなら §14 の仮説は少人数調査でしか検証できないと割り切る |

## 8. Opus の見解（壁打ちの結論）

| 論点 | 判断 |
|---|---|
| 軸 | Fable 案に同意。「帰る理由」はゲーム内の報酬ではなく**現実の時間・場所との接続**（実ISS軌道・暦・通過予告）に置く |
| 順序 | 描画の修正（進行中）→ 夜側コンテンツ（都市光・雷・月）→ 実ISS軌道＋暦＋通過予告（.ics） |
| 撮影の代替の「行為」 | 懸念 #2 に同意。画像を作らない**しおり（この瞬間の URL を1タップで残す／送る）**を採用候補に。軽く、共有にもなる |
| 安価で先に入れてよいもの | 就寝モード（#8）と「留守の間」の一行（#6）。ただし就寝時間はセッション長と別に数える |
| 初回の開始 | 懸念 #3 の折衷案（初回は日の出前、2回目以降は「いま」）を推奨 |
| 計測 | 公開トラフィックでの A/B は検出力不足。少人数の被験者内比較（§5.3）を主に。外部計測を入れるかはクライアント判断 |
